## 2. The Linux control panel: the browser Control Deck to parity

The desktop Control Panel is WPF and runs on Windows only; that will not change, and it should not - it is the best-in-class Windows administration program this server has. On Linux the administration surface is the browser Control Deck served at `/WebAdmin`, the REST API (81 routes, 40 of them administrative), and `hmailserver --set-admin-password`, `--create-database`, `--upgrade-database`. The Deck today has ten views - dashboard, domains, delivery queue, logs, rules, routes, certificates, ports, TLSA, settings - which is far more than Roadmap.md's row on it still says, and far less than the desktop program. ## 7. What the deep dive of 14 September found missing

Each of these was checked against Roadmap.md before it was written here: none has a row that ships it, and several have a row that says, in so many words, that it does not exist. Grouped by who feels the gap first.

### The administrator

| | Item | Detail |
|---|---|---|
| ⬜ | **Alerts** | Nothing tells an administrator anything unless they read a log or a metric. A queue that stalls, a disk that fills, a certificate a week from expiry, an auto-ban storm, a minidump, a backup that failed: each becomes a message to the administrator's address and a webhook, with a daily digest as the quiet default. The disk-space and work-queue tasks already know; they only log. |
| ⬜ | **Outbound webhooks** | The roadmap row says it plainly: no configurable webhook exists, only an event script an administrator writes by hand. A configured URL per event - message received, delivered, bounced, quarantined, account locked - with a signed body and retries. |
| ⬜ | **An audit trail** | Every administrative change - who, what, when, from where, over COM, REST or a page - in an append-only, hash-chained log the Deck shows. Exchange has it; a regulated customer asks for it first. |
| ⬜ | **Declarative configuration** | Export the whole configuration - settings, domains, accounts, rules, routes, certificates, listeners - as one file; apply one with a diff shown first; a GitOps loop that applies a repository on change. Stalwart's file and Postfix's main.cf are what people compare against, and the REST write surface is most of the work already done. |
| ⬜ | **The reports our own domains receive, read** | The server sends DMARC and TLS-RPT reports; it does not read the ones that come back for its own domains. A mailbox address per domain, the aggregate reports parsed, and a Deck page that charts who sends as the domain, with what result, the way dmarcian does for a fee. |
| ⬜ | **Own-reputation watch** | The server's outbound addresses checked against the major DNSBLs once a day, and an alert when one lists them - the first thing an administrator learns otherwise is a bounce. |
| ⬜ | **Compromised-account detection** | Per-account sending limits exist. What is missing is the shape of an account takeover: a sudden change in volume, recipients, hour or client address, which locks the account, keeps the mail in the queue for review and alerts. |
| ⬜ | **Outbound content policy (DLP)** | Rules on what leaves: card and account numbers by pattern, attachment types, size, an external recipient on a message marked internal - block, quarantine for review or warn the sender. Exchange has it; no open server does it well. |
| ⬜ | **Quarantine digests for users** | A daily message to each account whose quarantine holds something new, with one-click release from the webmail's held-mail page. |
| ⬜ | **PST import** | Every migration from Exchange and Outlook has a PST somewhere. A reader for the PST format in the import tool, so a migration is drag, wait, done. |
| ⬜ | **Event scripts on Linux** | The Windows build hosts VBScript and JScript through Active Scripting; the Linux build has no engine, and the roadmap's Linux row skips every scripting test for it. One cross-platform engine - JavaScript through an embeddable interpreter - for the same events on both, with the Windows engines kept. |
| ⬜ | **Passkeys and single sign-on** | Passkeys (WebAuthn) for the webmail and Deck sign-in with TOTP as the fallback; OIDC sign-in so an organisation's identity provider is the front door. The server already validates bearer tokens for SMTP and IMAP; the pages should take the same identity. |
| ⬜ | **A password checked against known breaches** | At every password change, the k-anonymity check against the breach corpus (five characters of the hash leave the server, nothing else), refused when found. |
| ⬜ | **Spam traps** | Addresses that were never real; a message to one auto-bans the sender and trains the score. |

| | Item | Detail |
|---|---|---|
| ⬜ | **Active-active nodes** | The warm-standby topology is documented and tested; what remains is two or more nodes serving the same domains at once - shared database, shared or replicated message store, queue ownership by node, sessions on any node - so a node can be taken down without a failover. |

## 9. End-to-end encryption

Transport is done: TLS everywhere, DANE, MTA-STS, a post-quantum key exchange, and S/MIME in the page since 11 September. What is not done is mail that stays unreadable to the server itself, and to anyone who takes the server. Proton and Tuta built businesses on that; theirs is proprietary in the sense that only their client reads their format. This server's version is built on OpenPGP, so that any client with a key reads the mail and no one is locked in - the standard is the feature. Roadmap.md deferred OpenPGP in the browser on 11 September as "the S/MIME page's design on another format"; it is un-deferred here, as the first row of the four.

| | Item | Detail |
|---|---|---|
| ⬜ | **OpenPGP in the page** | The S/MIME module's shape - keys made or imported in the browser, kept encrypted under a passphrase, unlocked for a session - for OpenPGP: sign, encrypt, decrypt, verify, with the lock and the signature badge the S/MIME messages already show; a key page with fingerprints, expiry and revocation; Autocrypt headers on outgoing mail so a correspondent's client learns the key, and Autocrypt read on incoming; keys of correspondents looked up by WKD and, where a domain has none, by a keyserver. Interoperates with Thunderbird, GnuPG, Mailvelope, Proton and every client that speaks the standard. |
| ⬜ | **The server publishes its users' keys** | Web Key Directory for every domain the server hosts: `/.well-known/openpgpkey/` on the web-services listener, advanced method, so that any client on the internet finds a user's key from the address alone. The keys are the ones made in the page or uploaded by an administrator for a client that keeps its own. |
| ⬜ | **Zero-access mailboxes** | Opt-in per account, the Proton model: after the filters have run - spam, virus, rules, which need the text - a delivered message is encrypted to the account's public key and the plaintext never touches the disk; the private key is encrypted under a key derived from the password with Argon2id and unlocked in the browser, and a recovery key the user writes down is the only other way in. The administrator cannot read the mail, cannot search it, and cannot recover it. Written down as the trade-offs it is: search runs over the client's own index or the headers the server kept; IMAP and POP see ciphertext, so an account with this on is a webmail account until a local bridge exists; a forgotten password without the recovery key is the mail lost, and the page says so before it is switched on. |
| ⬜ | **A password-protected message to anyone** | For the correspondent with no key: the sender sets a password, the page encrypts the body and attachments (OpenPGP, symmetric) and sends a short message with a link to a reading page on this server; the recipient enters the password there and the browser decrypts; a reply written on that page goes back the same way. End to end, because the plaintext is never in the message that crosses the internet and never on this server; unlike "confidential mode", it promises only what it can keep. |
| ⬜ | **Trust made visible** | A correspondent's key is remembered the first time it is seen and a change is a warning in the reader, not a silent switch - the one thing a man in the middle needs is silence. Fingerprints shown, verifiable by voice or in person, and a green mark on a verified correspondent from then on. |

## 11. Learning it: tutorials, tours and in-product help

Everything below is about the first hour, which is the hour this product currently spends worst. A new
administrator meets a Control Panel of forty-seven pages, a Deck of ten views and a webmail, and the help is
a wiki in another window. Nothing here is a mail feature; all of it is why a good mail server gets returned.
The Welcome page's twelve intents and the setup verdict on the dashboard are the ground this builds on.

| | Item | Detail |
|---|---|---|
| ⬜ | **Tutorial helper functions** | One mechanism, in all three surfaces, for teaching a page while somebody uses it: a step that can point at any control by its automation id or its element id, say one sentence, wait for the thing to happen, and move on; a tour built as a list of those steps; a "show me" link on any page that starts the tour for that page; and a record of which tours this administrator has finished, kept where the theme and the window bounds are kept. It must be refusable and resumable, never modal, never in the way of the keyboard, and it must survive the page being in another language - so every step's text goes through the catalogues like every other text. The Control Panel has the automation ids already (every page, every field), the Deck and the webmail have element ids and a design system; what nothing has is the stepper, the highlight and the store. |
| ⬜ | **The first-run walk, in each surface** | Built on the helpers above: the Control Panel walks a new administrator through a domain, an account, a listener and a certificate, and ends on the dashboard verdict; the Deck walks the same path in a browser; the webmail walks a new reader through the reading pane, the compose window, labels and search. Each is a list of steps, not a video and not a wizard that takes the keyboard away, and each ends where the person wanted to be rather than where it started. |
| ⬜ | **Help where the question is** | A help button on every page that opens what the wiki says about that page, beside the page rather than instead of it, and the same text offline in the binary so a server with no route to the Internet is not a server with no documentation. The Ctrl+K palette already matches a page's purpose sentence; this is the other direction. |
| ⬜ | **A sample domain that can be thrown away** | One command - and one button on the Welcome page - that makes `example.test` with three accounts, a distribution list, a rule and a handful of delivered messages, so that every page has something in it while somebody is learning, and one that removes all of it afterwards and says what it removed. The regression suite builds exactly this for itself several hundred times a day; nothing offers it to a person. |
| ⬜ | **A checklist that knows what is done** | The dashboard says whether the setup is sound; it does not say what to do next. A short list - a domain, an account, TLS on the submission port, SPF, DKIM, DMARC, a backup destination, an administrator second factor - each row checked against the server rather than ticked by hand, each with the page that finishes it. ## 12. The enterprise questions nothing here answers yet

Section 10 covers most of what a buyer asks. These are the ones it does not, found by walking the same comparison again with a procurement checklist rather than a feature list. Each is genuinely absent, checked against the code rather than remembered.

| | Item | Detail |
|---|---|---|
| ⬜ | **Rooms and equipment** (Exchange resource mailboxes) | A mailbox that is a meeting room or a projector: it accepts or declines an invitation by policy - free at that time, inside the booking window, from someone allowed to book it - rather than by a person reading mail. CalDAV landed on 15 September 2026 and is the ground for it; the row needs the resource account type, the booking policy, and the automatic reply that iMIP will carry. Nothing schedules anything today. |
| ⬜ | **Distribution lists that define themselves** | A list whose members are a query - every account in a domain, everyone with a given directory attribute - evaluated when a message is sent to it rather than maintained by hand. The static list is there, with moderation; the query is not. |
| ⬜ | **Devices, listed and revocable** | Every client that has signed in to an account, by protocol, address and last use, shown to the account holder and to the administrator, with a button that ends the session and revokes the application password behind it. The sessions and application passwords are both there and both listed; what is missing is the device as the thing a person recognises, and the one press that answers "my phone was stolen". |
| ⬜ | **Throttling per destination, and per tenant** | A message to a provider that is deferring should slow down for that provider and for nobody else, and one tenant should not be able to spend the whole server's outbound capacity. Per-account and per-domain sending limits exist; the outbound queue has no per-destination concurrency, no back-off that reads the remote's 4xx text, and no per-tenant share. |
| ⬜ | **Attachments opened somewhere safe** | ClamAV says whether a file is known to be bad. The question an enterprise asks is what an unknown file does when it is opened, which means handing it to a sandbox and holding the message until the answer comes back - a route to an external service, a hold that is not a quarantine, and a verdict that can arrive minutes later. |
| ⬜ | **SNMP** | The metrics are Prometheus and OpenTelemetry, which is right for anything built this decade and wrong for the monitoring system a bank already owns. An SNMP agent answering the mail MIB (RFC 2789) beside them, read-only, off by default. |
| ⬜ | **A migration that survives being interrupted** | The mirror collects one account's IMAP folders and the import tool reads mbox and Maildir. A migration of five hundred mailboxes from Microsoft 365 needs what neither has: a job per mailbox with a state, throttling the source will tolerate, a resume after a network failure or a restart, a report per mailbox, and contacts and calendars beside the mail. |
| ⬜ | **An upgrade nobody has to book a window for** | The installer stops the service, and a live update stops it too. With active-active nodes (section 7) an upgrade is a rolling restart; without them it is still possible to drain the listeners, finish the sessions in flight, apply the schema step and come back - which is minutes of refused connections rather than an outage, and it is not what happens today. |
| ⬜ | **A quota policy, not a quota** | An account has a maximum size. An enterprise wants the warning at eighty per cent in the reader's own language, the grace that still accepts incoming mail for a while, the point at which sending stops before receiving does, and a report of who is near the line - per domain, set once. |
| ⬜ | **The evidence pack** | `hmailserver/docs/RegulatoryScope.md` answers the Cyber Resilience Act and the Product Liability Directive. A buyer's security questionnaire asks a different set of questions - ISO 27001 and SOC 2 control mappings, the SBOM and provenance story in one place, the vulnerability handling policy, the release and signing chain, the data flows and where mail is stored. Every one of those facts exists in this repository; none of them is in a document somebody can send to a procurement team. |

## 13. The settings themselves

Where a setting lives, who may change it, when it takes effect and what it was before. The server has two
stores: `hm_settings` in the database, which the COM `Settings` object and the Control Panel's classic pages
have always used, and the `[Settings]` section of `hMailServer.ini`, which is where nearly everything this
fork has added since 6.2.10 went - 238 keys today, every one with a Control Panel editor and a REST route
(`/api/v1/settings/ini`), and every one still a line in a file. Schema 6011 added `hm_inisettings` and a
reconciliation, but as a **mirror**: the file is read, the table is written to match, and every reader still
reads the file. The rows below finish that job and the questions around it.

| | Item | Detail |
|---|---|---|
| 🔄 | **The database is the settings store; the file is the bootstrap** | **The rule since 15 September 2026: a new setting goes in the database, and no new key is added to `[Settings]`** - written in `.github/CONTRIBUTING.md` where a contributor meets it. What is left is the migration of the 238 that are already there. Flip the precedence that `hm_inisettings` was built for. The file keeps only what is needed to reach the database and to be let in without one - `[Directories]`, `[Database]`, `[Security]`'s administrator password and second-factor secret - and every other key is read from and written to the database, so a setting is administered like a domain or an account rather than by editing a file on the server. A key left in the file for a database-backed setting becomes a deliberate override, honoured and written to the log by name at every start, because a support engineer needs that door and nobody should walk through it by accident. The upgrade is one schema step: take what the file has, put it in the table, and leave the file saying where its settings went. **Why it matters beyond tidiness:** two nodes cannot share a file (section 7's active-active depends on this), a configuration backup that does not include the file is not a backup of the configuration, a Control Panel on another machine cannot read a file it has no share to, and the Deck and the REST API can only write what the server can reach. `IniFileSettings` is already the one seam every section is read through - `build/check-ini-coverage.py` proves it on every pull request - so this is a change behind that seam and not 238 changes in front of it. The five readers that go to the file directly are known and named in the header: the two DAV redirects, `UseLanguage`, the Control Panel when it runs on the server itself, `hmconfig.ps1`, and `hMailServer.exe /Register`, which runs with no database at all. |
| ⬜ | **A setting that takes effect when it is saved** | Today every `[Settings]` key is latched into a typed member when the service starts, so a change is persisted now and applied at the next start - which is what the Control Panel means by "applies after a service restart", and what an administrator reads as "this product cannot be configured while it is running". With the store in the database a save can publish: `LoadSettings` re-runs behind a lock, each subsystem that can take a new value takes it, and the ones that genuinely cannot - a listener's port under a live socket, the database connection itself - are marked in the settings index and keep the restart they need, with `POST /api/v1/server/reinitialize` as the way to take them without stopping the service. The index that would carry that mark is generated already (`build/generate-settings-index.ps1`). |
| ⬜ | **One value, three levels** | A handful of settings can already be set per domain (the relay, the limits, the signature); most are server-wide because that is where they were written. The shape people expect from a hosted product is server, then domain, then account, each overriding the last, with the **effective** value and where it came from shown beside the field - which is also the only honest way to answer "why is this account not doing what the domain says". Needs the store above first: a per-domain value has nowhere to live in a file that has one section. |
| ⬜ | **What changed, when, and who changed it** | Section 7's audit trail covers administrative actions; this is the settings half of it, and it is what a change-control process asks for: the key, the value before, the value after, the administrator, the address they connected from, and the ability to see the last fifty changes on a page or to put one back. A key-value table with history is a table with a second table beside it, and the REST layer already knows which route wrote what. |
| ⬜ | **What this server has changed from stock** | One page, and one line of `hmctl`, that lists every setting whose value is not the shipped default, with the default beside it. It is the first thing anybody asks when a server behaves oddly, the first thing to put in a support message, and the honest diff between two installations. Every default is already in the code as the third argument of the read; the list is what is missing. |
| ⬜ | **Configuration from the environment, for every setting** | The container image takes about twenty settings as `HM_*` environment variables and writes them into the ini on start; a Kubernetes user expects that of every setting, and expects a Secret to be able to supply any of them as a file. With the database as the store the entrypoint seeds the database instead of rewriting a file, which also settles what happens when the environment and the stored value disagree: the environment is the deployment's intent and wins on start, and the log says which values it overrode. |
| ⬜ | **Profiles, so a new server starts in the right shape** | The defaults suit one kind of deployment. A named profile - a small office server, a server behind a filtering gateway, an outbound relay, a high-volume sender - applied at setup or from the Deck, that sets thirty settings at once and says exactly which thirty and what they were, with a diff before it is applied and a way back. The setup wizard asks none of this today, and a new administrator is left to find each one. |

## 14. What a mail platform is asked to do, and this one does not

A third sweep, this time from the question an integrator asks rather than the one an administrator or a
reader asks: what does an application, a deliverability team or a compliance officer need from the server
that it cannot get today? Each row was checked against the code before it was written, and each says what
exists so that the gap is the only claim in it.

| | Item | Detail |
|---|---|---|
| ⬜ | **Mail in, to a webhook** (SendGrid and Mailgun call it inbound parse) | The outbound half is section 7's webhooks row. This is the other direction and it is what an application actually buys a mail server for: an address, or a whole domain, whose mail is parsed - sender, recipients, subject, text, HTML, attachments, the verdicts - and posted as JSON to a URL, with the same signature, retries and dead letter as an outbound webhook, and with a size ceiling and an attachment policy of its own. The rule already has "run a script"; nothing has "post it somewhere". |
| ⬜ | **A send API for applications** | `POST /api/v1/me/messages` sends as the signed-in account and is the webmail's. What an application wants is a server-level route with an API key of its own, a per-key sender it may use and may not exceed, per-key rate limits and a queue it can ask about afterwards - "was message X delivered, deferred or bounced, and why" - which is the message trace the server already keeps, per key. Without it every application that wants to send through this server speaks SMTP with an application password, which works and tells them nothing. |
| ⬜ | **Bounces read, and a suppression list** | The server retries and gives up; it does not read the DSN that comes back. A bounce classified (a mailbox that does not exist, a mailbox that is full, a policy refusal, a temporary failure) against RFC 3463's codes, counted per address, and an address that has hard bounced put on a suppression list that the next send is checked against - per domain, visible, and removable by hand. Sending to a known-dead address is how a sender's reputation is spent. |
| ⬜ | **Complaints, read** (the feedback loops) | The large mailbox providers send an abuse report (RFC 5965, `message/feedback-report`) when a recipient presses "this is spam". This server has nowhere for one to arrive: a mailbox per domain that parses them, counts them by sending account and campaign, adds the complainant to the suppression list above, and warns when the rate crosses the threshold the provider publishes. Deliverability is mostly this. |
| ⬜ | **DKIM keys that rotate** | A key is generated once, written to a file and used until somebody remembers. What is needed is the ordinary practice: two selectors live at once, a new key published and given time to propagate, signing moved to it, the old one kept for the reports that arrive late and then removed - on a schedule, per domain, with the DNS the administrator must publish shown at each step and checked from the resolver before the switch. The DNS-record view already knows how to show and verify a record. |
| ⬜ | **A backup that is encrypted** | The backup writes an archive with the system 7-Zip and verifies it by extracting it; nothing encrypts it. An archive that holds every mailbox on the server is the most concentrated copy of the data there is, and it is written to whatever destination an administrator typed - often a share, sometimes a cloud mount. A passphrase or a key, the archive encrypted as it is written, and the restore asking for it, with the key never stored beside the archive. |
| ⬜ | **A calendar shared with somebody** | CalDAV landed on 15 September 2026 with one calendar per account and no way to give another person sight of it. What an organisation asks for next, in order: free-busy for everyone in the domain (which is also what a room booking needs, section 12), a calendar shared read-only with a named account or a group, and a delegate who may write it and answer invitations on the owner's behalf. The WebDAV ACL layer the address books and calendars sit on is where it goes. |
| ⬜ | **An out-of-office policy, not just a message** | An account has an automatic reply, a subject, a body and an expiry date. An organisation needs the policy around it: a reply to people inside the organisation only, or a different text for them; one reply per sender per period rather than per message; no reply to a list, an automatic message or a null sender (some of which the delivery path already refuses); a default set for the domain; and an administrator able to set one for somebody who has left without signing in as them. |
